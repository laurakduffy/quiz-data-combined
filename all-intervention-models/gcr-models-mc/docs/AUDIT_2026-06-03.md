## Calculations verified

### `_solve_r_max` round-trips exactly
The vectorized bisection in `gcr_model.py` backs out the Gaussian peak annual risk `r_max`
that reproduces a target `cumulative_risk_100_yrs`. Across 2,000 random
`(cum, year_max_risk, year_risk_1pct_max, r_inf)` combinations spanning the prior ranges, the
reconstructed cumulative risk matched the target to a **median absolute error of ~1e-16**
(machine precision).

### Stellar-value continuity (uncommitted `b2` fix — verified correct)
At the time of audit the working tree contained an **uncommitted change** to the stellar-value
coefficients in `gcr_model.py`:

- `v_s` changed from "Earth value at `T_c`" → `carrying_capacity` (equivalent once the logistic
  has saturated, which it always has by `T_c` ≈ 100–500 yr).
- `b2` changed from `r_g * (d_g - d_s)` → `4/3·π·r_g³·(d_g - d_s)·v_s`.

The **old `b2` was dimensionally wrong** (missing the `4/3·π·r_g²` volume factor and the
per-star value `v_s`). The new formula is the correct continuity correction at the Milky-Way →
Virgo-supercluster handoff `T_s`; it follows from requiring
`a1·(T_s − T_c)³ = a2·(T_s − T_c)³ + b2` and the fact that `T_c ≪ T_s` (so
`(T_s − T_c)³ ≈ T_s³ = r_g³/s³`). Numerically the stellar value is continuous across `T_s` to a
relative gap of ~1e-5 (exactly the `(T_s − T_c)³ ≈ T_s³` approximation residual).

**Action: this fix should be committed.** It was verified correct during the audit.

## Confirmed-intentional design choices (not issues)

These were flagged during the audit and **confirmed intended** by the model owner:

1. **Sentinel Bio and Longview Nuclear are parameterized near-identically.** Their sub-extinction
   tiers produce byte-for-byte identical results, and their extinction rows differ only via
   `year_effect_starts` and the cause-fraction Dirichlet component. This reflects deliberate
   agnosticism about which of bio/nuclear is more effective (see "Same as Sentinel" comments in
   `param_distributions.py`).

2. **Common random numbers across funds.** All three funds run from the same base seed and RNG
   stream, so they are perfectly correlated on shared world parameters. This is intended — it
   reduces variance in fund-to-fund comparisons. (The README's "independent draws" note refers to
   the per-batch seed increment, not to the funds.)

## Interpretation caveats (expected behavior, documented for future readers)

These are inherent to the longtermist GCR model, not defects:

1. **The post-500-year / stellar term dominates total EV by ~14 orders of magnitude.** Short-period
   EVs (`t0`–`t4`) are numerically negligible relative to `after_500_plus`. The per-period columns
   are useful for transparency, but the total is effectively the long-run term.

2. **Per-period risk-adjusted columns are not, in general, additive.** They sum to the total here
   *only because one period dominates* — for nonlinear profiles (`wlu`, `dmreu`, `ambiguity`,
   `combined`) the risk-adjusted value of a sum ≠ sum of risk-adjusted values in general. Any
   downstream consumer that sums `t0..t5` is relying on the domination coincidence above, not a
   mathematical guarantee. Prefer the `total_*` columns / summary stats for fund scores.

3. **`r_inf` overshoot edge case (negligible).** When background risk `r_inf` alone exceeds the
   sampled `cumulative_risk_100_yrs`, `_solve_r_max` pins `r_max` to ~0 and the realized cumulative
   risk slightly overshoots the target. Under the production priors this affects ~0.003% of
   samples, all of which have ~zero intervention effect anyway. Not worth special-casing.

## Follow-up: how the per-period columns are consumed downstream

A follow-up trace confirmed how `gcr_output.csv` flows into the allocation:

```
gcr_output.csv
  → combine_data.py / sensitivity-analysis/gcr-params/gcr_combine_data.py
      build a 6 time-period × 9 risk-profile `values` matrix per effect in the dataset JSON
  → run_gcr_alloc.js → computeWeightedAllocation.js → marcusCalculation.js
  → src/utils/projectScoring.js  (calculateSingleEffect)
```

**The allocator does NOT read a `total_*` column.** It reconstructs each fund's score by
summing the per-period risk-adjusted cells, each scaled by a worldview's per-period discount
factor (`src/utils/projectScoring.js`):

```js
for (let t = 0; t < 6; t++) {
  sum += values[t][riskProfile] * discountFactors[t];
}
return moralWeight * sum;
```

So the "per-period risk-adjusted columns are not generally additive" caveat (above) **is**
exercised by the consumer. This is **not a defect**, for two reasons:

1. **Per-period storage is required, not optional.** Keeping periods separate is what lets a
   worldview apply its own time-discount factors per period. A single pre-aggregated `total_*`
   value could not support per-period discounting — so "use the total column instead" is not a
   valid alternative.
2. **The imperfection is swamped by domination.** Because the 500+ year period (`t5` =
   `after_500_plus`) out-scales the others by ~14 orders of magnitude, every fund score is
   effectively `discountFactors[5] × riskadjust(long-term distribution)`. The theoretical gap
   between "risk-transform each period then sum" and "risk-transform the discounted-summed
   distribution" is negligible relative to the dominant term.

**Practical takeaway:** the GCR fund ranking pivots on `discount_factors[5]` (the 500+ period
weight). Zeroing it collapses GCR funds to the short-term survival scale (~1e6); any nonzero
long-term weight lets the long-term term dominate. This is the intended longtermist behavior.

Profile-column ordering is consistent between `combine_data.py` and `gcr_combine_data.py`
(neutral, wlu low/mod/high, upside, downside, combined, ambiguity, ambiguity bilateral;
`dmreu` is deliberately excluded from the JSON matrix), so the production and sensitivity
pipelines agree.

Stale comments corrected during this follow-up (cosmetic, no behavior change):
`src/utils/projectScoring.js` JSDoc ("6 × 4 … index 0-3" → "6 × 9 … index 0-8") and
`combine_data.py` ("6x8 values matrix" → "6x9").
